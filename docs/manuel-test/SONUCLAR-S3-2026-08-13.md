**Kök neden**

**Kanıt**

## HATA-S3-008 — İdempotency tekrar (`replay`) yanıtı orijinal HTTP başlıklarını (`Location`, `Preference-Applied`) kaybediyor

- **Case:** MT-JOB-083
- **Önem:** Orta
- **İzlek:** B
- **Ortam:** macOS arm64 · net10 · PostgreSQL · OpenAI

**Beklenen**
Aynı `Idempotency-Key` ile `Prefer: respond-async` isteği iki kez
gönderildiğinde, ikinci (tekrar/`replay`) yanıt ilk yanıtla — `Location`
başlığı dahil — HTTP düzeyinde birebir aynı olmalıdır.

**Gerçekleşen**
İkinci yanıtın JSON gövdesi (`runId`/`jobId`/`location`/`eventsLocation`)
ilk istekle birebir aynı ve `Idempotency-Replayed: true` başlığı doğru
eklenmiş — AMA `Location` VE `Preference-Applied` HTTP başlıkları ikinci
yanıtta **hiç yok**.

**Kök neden**
`src/AgentPrism.Abstractions/Idempotency/IdempotencyTypes.cs:45-56`,
`IdempotencyResponse` yalnız `StatusCode`, `ContentType`, `Body`, `RunId`
alanlarını taşıyor — hiçbir HTTP başlığı saklamıyor.
`src/AgentPrism.AspNetCore/Idempotency/IdempotencyResults.cs:12-19`,
`IdempotencyReplayResult.ExecuteAsync` yalnız `StatusCode`, `ContentType`
ve `Idempotency-Replayed` başlığını ayarlayıp gövdeyi yazıyor. İlk
isteğin ürettiği `Location`/`Preference-Applied` başlıkları
`IdempotencyCapturingResult.ExecuteAsync`'te (aynı dosya) hiç
YAKALANMIYOR — yalnız gövde baytları (`buffer.ToArray()`) ve durum kodu
saklanıyor, `httpContext.Response.Headers` hiç okunmuyor.

**Yeniden üretme**
1. `Prefer: respond-async` + `Idempotency-Key: X` ile `POST
   /api/agents/{name}/run` gönder — `Location` başlığı gelir.
2. Aynı `Idempotency-Key: X` ile TEKRAR gönder.
3. İkinci yanıtta `Location` başlığı **yoktur** (gövdedeki `location`
   alanı doğru olsa da).

**Kanıt**
- İlk yanıt başlıkları: `Location: /agentprism/api/runs/<runId>`,
  `Preference-Applied: respond-async`.
- İkinci (replay) yanıt başlıkları: yalnız `Idempotency-Replayed: true`
  — `Location`/`Preference-Applied` yok.

**Kapsam**
Yalnız `Prefer: respond-async` + `Idempotency-Key` kombinasyonunu
etkiler (diğer idempotency kullanım yolları — OpenAI uyumlu uçlar gibi —
zaten `Location` üretmez). HTTP-spesifikasyonuna sıkı uyan istemciler
(`Location` başlığını gövdeden değil başlıktan okuyanlar) ikinci
istekte konumu kaybeder. Düzeltme önerisi: `IdempotencyResponse`'a bir
`Headers` alanı eklenip yalnız beyaz listeye alınmış başlıklar
(`Location`, `Preference-Applied`) saklanmalı/tekrarlanmalı.

## HATA-S3-009 — `RunsRead`-kapsamlı bir API anahtarı zamanlama oluşturabiliyor ve silebiliyor (`SchedulingEndpoints` kapsam kontrolü yok)

- **Case:** MT-JOB-090
- **Önem:** Yüksek
- **İzlek:** B
- **Ortam:** macOS arm64 · net10 · PostgreSQL

**Beklenen**
Yalnız `RunsRead` kapsamlı bir API anahtarı, `SchedulingEndpoints`
üzerinden yazma işlemleri (zamanlama oluşturma/silme) yapamamalıdır —
`403 Forbidden` beklenir.

**Gerçekleşen**
`RunsRead`-kapsamlı bir anahtarla: `PUT /api/schedules/kapsam-testi` →
`HTTP:200` (oluşturuldu). `DELETE /api/schedules/kapsam-testi` →
`HTTP:204` (silindi). Kontrol grubu `PUT /api/agents/...` (aynı anahtar)
→ `HTTP:403`, `"Bu uc 'AgentsAdmin' kapsamini gerektiriyor..."` — kapsam
sistemi `AgentEndpoints`'te ÇALIŞIYOR, `SchedulingEndpoints`'te HİÇ
DEVREDE DEĞİL.

**Kök neden**
`grep -n "RequireApiKeyScope" src/AgentPrism.AspNetCore/Endpoints/SchedulingEndpoints.cs`
boş döner — bu dosyanın hiçbir ucu `RequireApiKeyScope(...)` çağırmıyor.
`AgentPrismEndpointFilter.CheckScope`, kapsam metadata'sı yoksa denetimi
koşulsuz geçiriyor. Rol politikaları da örnek uygulamada kayıtlı
olmadığı için (bkz. `00-INDEKS.md` §8), bu kapsam boşluğu tek savunma
katmanının yokluğu anlamına geliyor.

**Yeniden üretme**
1. Yalnız `RunsRead` kapsamıyla bir API anahtarı üret
   (`POST /api/api-keys`, gövde alanı `plaintextKey` — `rawKey` DEĞİL,
   doküman kusuru ayrıca düzeltildi).
2. Bu anahtarla `PUT /api/schedules/{ad}` çağır — `200` döner.
3. `DELETE /api/schedules/{ad}` çağır — `204` döner.
4. Kontrol: aynı anahtarla `PUT /api/agents/{ad}` çağır — `403` döner
   (kapsam sistemi ORADA çalışıyor).

**Kapsam**
`15-WORKFLOWS.md` `MT-WF-100`'ün `WorkflowEndpoints` için bulduğu
BİREBİR AYNI kalıp — artık İKİ bağımsız uç grubunda (Workflow +
Scheduling) doğrulanmış sistematik bir boşluk. Üçüncü, kontrol
edilmemiş uç gruplarında da (örn. `WebhookEndpoints`,
`RetentionEndpoints`) muhtemelen aynı boşluk vardır — `RequireApiKeyScope`
eksikliğini tarayan sistematik bir denetim (tüm `MapPut`/`MapPost`/
`MapDelete` çağrılarının kapsam metadata'sı taşıyıp taşımadığını
kontrol eden bir derleme-anı/test-anı analiz) önerilir.
